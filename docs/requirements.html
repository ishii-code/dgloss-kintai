jinjer 全面置き換えロードマップ

jinjer（人事労務・給与を含むSaaS一式）を段階的に自作システムへ置き換えるための、スコープ・優先度・フェーズ計画。「何を自作し、何を作らず、どの順で作るか」をここで確定する。

版 v0.1（ドラフト） 対象 就業規則・賃金規程 2025.07.01 担当 石井 現状 勤怠コア 本番稼働中
01

背景と目的

なぜ自作するのか

jinjer は計算ロジックを開示しない。割増賃金・控除の計算を内製して初めて、就業規則・賃金規程を「正」とした計算の正しさを自社で担保できる。計算ミスは未払い賃金＝労基法違反に直結するため、ここは外部任せにしない。

jinjer は敵ではなく武器

当面は jinjer を残し、同じ打刻を自作エンジンと jinjer 両方で締めて 1 円単位で自動突合（Shadow Mode）。jinjer を「正解データ」に回帰テストして自作の精度を上げ、確信が持ててから解約する。移行の pull にも使う。

スコープ方針。 jinjer 全機能を一度に作らない。既存の勤怠・賃金エンジンを核に段階拡張し、モジュールごとに「自作する／jinjer・専門SaaSを継続する／対象外」を明示的に判断する。特に税・社会保険の年次手続は法改正が毎年入る重量級領域で、自作はコスト・リスクが高い。

05

要確認事項（経営判断が必要）

Q1
税・社会保険まで自作するか。 給与計算の所得税・社保料、年末調整、社保電子申請、労働保険年度更新は毎年の法改正対応が必要。推奨：当面 jinjer/専門SaaS を継続し、勤怠〜給与総支給までを自作。
Q2
権限モデル。 現状は共有iPadのキオスク型ログイン。管理者/承認者/一般の権限、なりすまし防止、監査ログをどこまで求めるか。
Q3
給与の税・社保計算の入力元。 自作する場合、税額表・保険料率・扶養情報のメンテ体制。しない場合、総支給までを出力し jinjer/給与ソフトへ連携。
Q4
jinjer 解約の時期。 Shadow 突合で何か月一致したら解約するか（例：3か月連続一致）。移行データの範囲（過去何年分）。
Q5
経費・ワークフローの要否。 経費精算やプロジェクト費用負担を自作対象に含めるか。
06

非機能要件

技術・品質

  • Next.js + TypeScript(strict, any禁止) + Tailwind + Prisma
  • 金額は bigint 整数演算・1円単位（浮動小数排除）
  • 入力は zod 検証必須・raw SQL 禁止
  • 就業規則/賃金規程を唯一の仕様とし、config で会社固有値を外出し

運用・非機能

  • 認証・権限（Phase 4 で強化）、監査ログ
  • 個人情報・給与データの保護、アクセス制御
  • Shadow 突合による回帰検証で未払いリスク検知
  • UI は peco-ui（#FCB900/#FF6900）・iPad 優先
